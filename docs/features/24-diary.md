# 24. 다이어리 (일기) ⬜

## 상태
⬜ 시작 안함 — 계획 수립 완료

---

## 개요

매일의 일상을 기록하는 기능. 사진·영상을 첨부할 수 있으며,
첨부 미디어는 **사용자별 월간 한도**와 **계정 누적 한도**(둘 다 용량 기준)로 제한된다.
한도는 구독 등급(`free` / `adFree` / `premium`)에 따라 달라지며,
**프리미엄 구독의 전용 혜택**으로 한도를 크게 늘린다.

### 설계 철학 — 기록의 마찰을 없앤다

일기 앱의 실패는 대부분 기능 부족이 아니라 **"쓰기 시작하는 부담"** 때문이다.
3일 쓰고, 일주일 비고, 안 쓴다. 날짜·기분·날씨·제목·본문을 갖춘 폼을 열게 만드는 순간
그 앱은 "각오해야 여는 앱"이 된다.

그래서 이 기능은 **입력의 자유도와 저장 단위를 분리**한다.

```
사용자는 아무 때나 조각을 던지고  →  시스템이 그날 문서에 모은다
```

- **던지기(빠른 기록)**: 목록 하단 입력창에 한 줄 또는 사진 하나. 화면 전환도 저장 버튼도 없다.
- **모으기(하루 1편)**: 던진 조각은 그날 일기에 시각과 함께 **append**된다.
- **다듬기(작성 화면)**: 밤에 열면 조각이 이미 본문에 있다. **백지에서 시작하지 않는다.**

작성 화면의 위상이 "쓰는 곳"에서 **"다듬는 곳"** 으로 바뀐다는 것이 핵심이다.

### 핵심 결정사항

| 항목 | 결정 |
|------|------|
| 기본 입력 | **빠른 기록(Quick Capture)** — 목록 하단 고정 입력창, 즉시 append |
| 저장 단위 | **하루 1편** — `(userId, date)` 유니크. 조각은 문서 안의 블록으로 누적 |
| 하루 경계 | **새벽 4시 기준** (새벽 3시 기록은 전날 일기로) |
| 공개 범위 | 메모와 동일하게 **PRIVATE / GROUP** 선택 |
| 본문 포맷 | Quill **DELTA JSON** (메모와 동일 — 에디터/뷰어 재사용) |
| 한도 기준 | **용량(bytes)** — 월간 한도 + 계정 누적 한도 |
| 한도 검증 위치 | **서버가 최종 권한** (클라이언트는 사전 안내용) |
| 압축 | 기본 ON, 사용자가 **"원본으로 업로드" 선택 가능** (한도가 억제 장치) |
| 업로드 경로 | **Presigned URL로 R2 직접 업로드** (서버 릴레이 아님) |
| 미디어 배치 | 본문 Delta에 임베드하지 않고 **별도 미디어 그리드**로 관리 |
| 날짜 처리 | `'YYYY-MM-DD'` 문자열 송수신 + 서버가 KST 기준 정규화 |

## 0. 기록 방식 — 빠른 기록과 하루 1편

### 0-1. 왜 조각을 던져도 "하루 1편"인가

빠른 기록을 넣으면 하루에 조각이 여러 개 생긴다. 여기서 두 갈래가 있는데,
**조각을 각각의 일기로 만들지 않는다.**

| | 조각 = 개별 일기 (하루 N편) | **조각 = 하루 문서의 블록 (채택)** |
|---|---|---|
| 목록 | 하루치가 7개 항목으로 흩어짐 | 하루 = 한 칸 |
| 캘린더 | 한 칸에 여러 개 → 표현 붕괴 | 한 칸 = 한 편 유지 |
| "정리하기" | 뭘 열어 다듬을지 모호 | 그날 문서 하나가 대상 |
| "n년 전 오늘" | 조각 여러 개를 어떻게 보여줄지 애매 | 한 편을 그대로 꺼냄 |

**하루 1편은 제약이 아니라 조각을 담는 그릇**이다. 입력은 자유롭고, 읽을 때만 하루로 묶인다.
`@@unique([userId, date])`가 여기서 오히려 유리하게 작동한다 — 던진 조각을
어디에 붙일지 고민할 필요가 없다.

### 0-2. 하루의 경계는 새벽 4시 ★

자정 기준이면 새벽 1시에 쓴 기록이 "내일 일기"가 된다. 사용자 체감과 어긋난다.
**하루 경계를 `04:00 KST`로 둔다.**

- 새벽 3시 59분 기록 → **전날** 일기
- 새벽 4시 00분 기록 → 당일 일기
- 구현: `date-kst.util.ts`에 `diaryDateInKst()`를 추가한다
  (현재 시각에서 4시간을 뺀 뒤 `todayInKst()` 로직 적용)
- 이 규칙은 **빠른 기록의 기본 날짜 산정에만** 적용한다.
  사용자가 날짜를 직접 고르면 그 값을 그대로 쓴다.
- 캘린더·통계·스트릭도 모두 이 경계를 따른다 (한 곳만 자정 기준이면 어긋난다)

### 0-3. 조각의 구조

조각은 별도 테이블이 아니라 **Delta 문서 안의 블록**이다.
`DiaryEntry` 같은 테이블을 새로 만들지 않는다 — 만들면 본문과 조각이 이원화되어
[4-1](#4-1-본문delta와-미디어의-경계-모호했던-부분)에서 피하려던 동기화 문제가 되돌아온다.

- 텍스트 조각: Delta에 문단 + 시각 마커 attribute (`{"diaryTime":"14:32"}`)
- 사진 조각: `DiaryMedia` 레코드 추가 (본문에는 넣지 않음 — 4-1 원칙 유지)
- 시각 마커는 뷰어에서 좌측에 작게 렌더링하고, **다듬기 모드에서 일괄 제거 가능**
  (정리해서 하나의 글로 만들고 싶은 사람을 막지 않는다)

### 0-4. 지난 날짜에 조각 추가 (Phase 2 이후)

어제 사진을 오늘 올리는 경우. 빠른 기록에서 날짜 변경을 허용하되,
**사진의 EXIF 촬영일이 오늘과 다르면 먼저 물어본다.**

```
이 사진은 9월 1일에 찍었어요.
[ 9월 1일 일기에 넣기 ]  [ 오늘 일기에 넣기 ]
```

- 자동으로 과거 날짜에 넣지 않는다 (스크린샷·저장한 이미지가 오탐을 만든다)
- EXIF가 없으면 묻지 않고 오늘로 간다

## 1. 구독 등급별 미디어 한도

| Tier | 월간 업로드 한도 | 계정 누적 한도 | 파일 1개 최대 | 영상 |
|------|-----------------|---------------|--------------|------|
| `free` | 100 MB | 500 MB | 20 MB | ❌ (이미지만) |
| `adFree` | 300 MB | 2 GB | 50 MB | ✅ 최대 60초 |
| `premium` | 2 GB | 20 GB | 200 MB | ✅ 최대 5분 |

> 위 수치는 **초안**이다. R2 실제 단가와 초기 사용 통계를 보고 출시 전 조정한다.
> 값은 앱에 하드코딩하지 않고 **서버가 내려주도록** 해서, 앱 재배포 없이 조정할 수 있게 한다.

### 한도 계산 규칙
- **월간 한도**: 매월 1일 00:00(KST) 리셋. `uploadedAt`이 이번 달인 미디어의 `fileSize` 합.
  - 리셋은 배치가 아니라 **조회 시점의 기간 집계**로 처리 (배치 실패 리스크 제거)
- **계정 누적 한도**: 현재 살아있는(삭제되지 않은) 미디어의 `fileSize` 합.
  - 일기/미디어를 삭제하면 **누적 한도는 즉시 회복**되지만 **월간 한도는 회복되지 않는다.**
    (업로드 트래픽 자체가 비용이므로. 이 규칙을 UI에 명시해야 문의가 줄어든다)
- **다운그레이드 시**: 이미 올린 파일은 삭제하지 않는다. 누적 한도 초과 상태면
  **신규 업로드만 차단**하고 조회·삭제는 그대로 허용 (데이터 인질 방지)

### 삭제 정책 — soft delete와 R2 실제 삭제 시점 ★확정 필요했던 부분

`deletedAt`만 기록하고 R2 파일을 남겨두면, **사용자는 한도를 돌려받았는데 우리는 저장
비용을 계속 내는 갭**이 생긴다. 이 갭을 방치하면 "지웠다 올렸다"를 반복해 실질 무한
용량이 된다. 그래서 다음으로 **고정**한다.

| 대상 | soft delete 유예 | R2 실제 삭제 | 누적 한도 회복 |
|------|-----------------|-------------|--------------|
| **일기 본문(Diary)** | 30일 (휴지통 복구 가능) | — | — |
| **미디어(DiaryMedia)** | **없음 — 즉시** | **즉시 삭제** | 즉시 |

- **일기는 복구할 수 있지만, 첨부 미디어는 복구되지 않는다.** 30일 안에 일기를 되살리면
  본문·기분·날씨는 그대로 돌아오고 미디어 자리에는 "삭제된 첨부"만 남는다.
- 삭제 확인 다이얼로그에 **"사진/영상은 즉시 삭제되며 복구할 수 없습니다"** 를 반드시 명시한다.
  (이걸 안 쓰면 CS가 들어온다. 문구 자체가 스펙의 일부다)
- 근거: 텍스트는 복구 가치가 크고 저장 비용이 0에 가깝지만, 미디어는 그 반대다.
  비용 구조가 다른 두 자원에 같은 정책을 쓸 이유가 없다.
- 미디어 개별 삭제(저장공간 관리 화면)도 동일하게 **즉시·영구**다.

## 2. 데이터 모델 (백엔드 — Prisma)

```prisma
model Diary {
  id         String          @id @default(uuid())
  userId     String
  groupId    String?
  date       DateTime        @db.Date          // 일기 날짜 (KST 기준, UTC 자정 정규화 — 3-1 참조)
  title      String?         @db.VarChar(200)  // 생략 가능 (없으면 날짜로 표시)
  content    String          @db.Text          // Quill Delta JSON
  plainText  String?         @db.Text          // 검색용 평문 (서버가 Delta에서 추출)
  format     DiaryFormat     @default(DELTA)
  visibility DiaryVisibility @default(PRIVATE)
  mood       String?         @db.VarChar(20)   // 기분 이모지/코드 (선택)
  weather    String?         @db.VarChar(20)   // 날씨 코드 (선택, weather 기능 연동)
  createdAt  DateTime        @default(now())
  updatedAt  DateTime        @updatedAt
  deletedAt  DateTime?

  user  User         @relation(fields: [userId], references: [id], onDelete: Cascade)
  group Group?       @relation(fields: [groupId], references: [id], onDelete: Cascade)
  media DiaryMedia[]

  @@unique([userId, date])                     // ★ 하루 1편 보장
  @@index([userId, date(sort: Desc)])
  @@index([groupId, date(sort: Desc)])
  @@index([deletedAt])
  @@map("diaries")
}

model DiaryMedia {
  id           String      @id @default(uuid())
  diaryId      String?                            // 업로드 직후엔 null (고아 파일 정리 대상)
  userId       String                             // 한도 집계는 diary가 아니라 user 기준
  type         MediaType                          // IMAGE | VIDEO
  status       MediaStatus @default(PENDING)      // ★ presigned 업로드 상태 (3-2 참조)
  storageKey   String      @db.VarChar(500)       // R2 key
  thumbnailKey String?     @db.VarChar(500)       // 영상 썸네일 / 이미지 축소본
  fileName     String      @db.VarChar(255)
  declaredSize Int                                // 클라이언트가 신고한 크기 (사전 검증·예약용)
  fileSize     Int?                               // ★ 한도 집계 기준 (R2 HeadObject 실측, 확정 후 채움)
  originalSize Int?                               // 압축 전 크기 (절약량 표시용)
  mimeType     String      @db.VarChar(100)
  width        Int?
  height       Int?
  durationMs   Int?                               // 영상 길이
  isOriginal   Boolean     @default(false)        // 원본 업로드 여부
  sortOrder    Int         @default(0)
  reservedAt   DateTime    @default(now())        // presigned 발급 시각 (만료 정리 기준)
  uploadedAt   DateTime?                          // ★ 월간 집계 기준 (완료 확정 시각)
  deletedAt    DateTime?

  diary Diary? @relation(fields: [diaryId], references: [id], onDelete: Cascade)
  user  User   @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@index([userId, uploadedAt])                   // 월간 집계용
  @@index([userId, deletedAt])                    // 누적 집계용
  @@index([userId, status, reservedAt])           // 만료된 PENDING 정리용
  @@index([diaryId, sortOrder])
  @@map("diary_media")
}

enum DiaryFormat     { DELTA PLAIN MARKDOWN }
enum DiaryVisibility { PRIVATE GROUP }
enum MediaType       { IMAGE VIDEO }
enum MediaStatus     { PENDING CONFIRMED }        // PENDING: 예약됨(업로드 중) / CONFIRMED: 완료
```

### 설계 근거
- `DiaryMedia.userId`를 별도로 두는 이유: 한도는 **사용자 단위**라 diary를 거치지 않고
  집계해야 하고, 업로드 직후 diary가 아직 없는 상태(임시 첨부)도 집계에 포함해야 한다.
- `diaryId`가 nullable인 이유: 사용자가 사진만 올리고 저장하지 않고 나가는 경우가 있다.
  이런 **고아 미디어는 한도를 계속 잡아먹으므로, 24시간 지난 `diaryId == null` 레코드를
  스케줄러로 R2에서 삭제**한다. (이 정리를 빠뜨리면 한도가 조용히 새어나간다)
- `declaredSize` / `fileSize`를 나눈 이유: presigned 방식에서는 서버가 바이트 스트림을
  보지 못한다. 발급 시점엔 클라이언트 신고값(`declaredSize`)으로 **자리를 예약**하고,
  완료 콜백에서 **R2 `HeadObject`로 실측한 값**을 `fileSize`에 채워 확정한다.
  **한도 집계는 언제나 `fileSize`(실측) 기준**이며, 신고값은 예약에만 쓴다.
  `HeadObject`는 백엔드 `storage.service.ts`에 이미 구현돼 있다(`fileExists`가 사용 중).
- `status`가 필요한 이유: presigned URL을 받고 업로드하지 않은 레코드는 실제 파일이
  없는데도 예약 용량을 잡고 있다. **`PENDING`인 채 15분이 지나면 정리**한다.

## 3. API 설계

### 3-1. 날짜·타임존 규약 ★반드시 먼저 합의할 것

`@db.Date`는 타임존 정보를 갖지 않는다. KST 2026-09-01 23:30에 쓴 일기를 서버가 UTC로
변환하면 `2026-08-31`이 되어, `@@unique([userId, date])`가 엉뚱하게 충돌하거나 조회가
하루씩 밀린다.

**이 프로젝트에는 이미 해결책이 있다** — `src/common/utils/date-kst.util.ts`.
루틴 기능이 `checkedDate`에 똑같은 문제를 겪고 만든 유틸이므로 **그대로 재사용한다.**

| 구간 | 규약 |
|------|------|
| 클라이언트 → 서버 | `date`를 **`'YYYY-MM-DD'` 문자열**로 보낸다. `DateTime.toIso8601String()` **금지** |
| 서버 파싱 | `parseDateOnly(dto.date)` → `new Date('YYYY-MM-DDT00:00:00.000Z')` |
| "오늘" 판정 | `todayInKst()` — 서버 로컬시각·UTC 기준 금지 |
| 월간 한도 경계 | `thisMonthStartInKst()` |
| 서버 → 클라이언트 | 응답도 **`'YYYY-MM-DD'` 문자열**로 내린다 (앱에서 `DateTime.parse` 시 UTC 해석 사고 방지) |
| 미래 날짜 | 서버가 `todayInKst()` 초과를 거부 (클라이언트 검증만 믿지 않는다) |

> Flutter 쪽도 동일하게, 모델의 `date`는 `DateTime`이 아니라 **`String`(YYYY-MM-DD)** 으로
> 두거나, `DateTime`을 쓴다면 반드시 `DateUtils.dateOnly()`로 정규화해서 시각 성분을
> 제거한다. 기기 타임존이 KST가 아닐 수 있다는 점(해외 체류·여행)도 고려 대상이다.
> **"오늘의 일기"의 기준은 사용자 기기 로컬 날짜**로 하고, 그 값을 문자열로 보낸다.

### 3-2. 미디어 업로드 — Presigned URL 직접 업로드 ★설계 변경

당초 `multipart/form-data`를 백엔드가 받아 R2로 릴레이하는 방식이었으나, **프리미엄 파일
최대 200MB + 영상**을 감안하면 모바일 네트워크에서 백엔드가 병목이 된다. Railway 인스턴스의
요청 타임아웃·메모리·동시 연결이 그대로 한계가 되고, 업로드 중 연결이 끊기면 처음부터 다시다.

**백엔드에 이미 `getUploadUrl()`(presigned PUT, 기본 10분)이 구현되어 있다**
(`storage.service.ts`). 새로 만들 필요 없이 그대로 쓴다.

```
[1] POST /diaries/media/reserve      (한도 검증 + 자리 예약)
      → 서버: Redis 락 → 한도 확인 → DiaryMedia(status=PENDING) 생성
      → 응답: { mediaId, uploadUrl(presigned PUT), storageKey, expiresIn }

[2] PUT <uploadUrl>                  (클라이언트 → R2 직접, 백엔드 경유 안 함)
      → 실패 시 [1]의 mediaId로 재시도 가능

[3] POST /diaries/media/:id/confirm  (완료 확정)
      → 서버: R2 HeadObject로 실제 크기·존재 확인
      → 실측 fileSize 기록, status=CONFIRMED, uploadedAt=now
      → 트랜잭션 내에서 한도 재확인 → 초과면 파일 삭제 후 402
      → 응답: 갱신된 quota + media 정보
```

| 메서드 | 경로 | 설명 |
|--------|------|------|
| `GET` | `/diaries/media/quota` | 현재 한도 상태 조회 (업로드 전 필수) |
| `POST` | `/diaries/media/reserve` | 한도 검증 + presigned URL 발급 |
| `POST` | `/diaries/media/:id/confirm` | 업로드 완료 확정 (실측 크기 반영) |
| `DELETE` | `/diaries/media/:id` | 미디어 삭제 (R2 즉시 삭제, 누적 한도 회복) |

**`reserve` 단계 검증 순서** (비용 큰 것부터 막는다)
1. `declaredSize`가 파일 1개 최대치 초과 → 413
2. tier가 영상 불가인데 `type=VIDEO` → 403 `VIDEO_NOT_ALLOWED`
3. 영상 길이 초과 → 400 (클라이언트가 메타데이터로 신고, `confirm`에서 재검증)
4. `mimeType` 화이트리스트 검증
5. **Redis 사용자 락** → 월간/누적 잔여 확인 (`CONFIRMED` + 유효한 `PENDING` 합산)
   → 초과 시 402 `QUOTA_EXCEEDED` (남은 용량 동봉)
6. `PENDING` 레코드 생성 + presigned URL 발급 (유효 10분)

**`confirm` 단계**
1. `HeadObject`로 실제 존재·크기 확인 — 없으면 400 (업로드 실패)
2. **실측 크기가 `declaredSize`보다 크면** → 한도 재검증, 초과 시 R2 파일 삭제 후 402
   (신고값 위조 방어. presigned 방식의 유일한 구멍이므로 여기서 반드시 막는다)
3. `Content-Type` 재확인 + 이미지/영상 메타데이터 추출
4. 트랜잭션 내 최종 한도 확인 → `CONFIRMED` 확정

> ⚠️ presigned URL은 발급 후 10분간 **그 키에 무엇이든 쓸 수 있다.** 그래서 `confirm`의
> 실측 검증이 필수다. 신고값만 믿으면 1KB로 예약하고 200MB를 올릴 수 있다.

> ⚠️ **정리 스케줄러 2종** — 둘 다 없으면 한도가 샌다.
> - `status=PENDING`이고 `reservedAt`이 15분 이상 지난 것 → 레코드 삭제 (+ R2 잔여물 제거)
> - `diaryId=null`이고 `CONFIRMED`된 지 24시간 지난 것 → R2·레코드 삭제

**웹(kIsWeb) 주의**: presigned PUT은 R2 버킷에 **CORS 설정**이 필요하다
(`PUT` 허용 + 앱 오리진 허용). 웹 지원 시점에 R2 콘솔에서 반드시 설정한다.

#### `POST /diaries/append` — 빠른 기록 ★

```json
// 요청
{
  "date": "2026-09-01",        // 생략 시 서버가 diaryDateInKst()로 결정 (새벽 4시 경계)
  "text": "점심에 본 고양이",     // 텍스트 조각 (선택)
  "mediaIds": ["uuid-1"],       // 이미 confirm된 미디어 (선택)
  "capturedAt": "14:32"         // 조각 시각 마커
}
```

- **upsert 동작**: 그날 일기가 없으면 생성하고, 있으면 Delta 끝에 append한다.
  클라이언트가 "오늘 일기가 있나?" 를 먼저 조회할 필요가 없다 (왕복 1회로 끝)
- `text`와 `mediaIds` 중 **최소 하나는 필수**
- 응답은 갱신된 일기 전체가 아니라 **추가된 조각 + 일기 id**만 (목록 낙관적 갱신용)
- 동시성: 같은 사용자가 연달아 던지면 `@@unique([userId, date])`에 걸릴 수 있다.
  **upsert를 트랜잭션 + 유니크 충돌 재시도**로 처리한다 (Prisma `upsert`는 경합 시
  P2002를 던질 수 있으므로 1회 재시도 필요)
- 공개 범위: 그날 일기가 이미 있으면 **기존 값을 따른다.** 새로 만들어질 때만
  사용자의 기본 설정값(설정에서 지정, 기본 PRIVATE)을 적용한다
  → 빠른 기록에서 매번 공개범위를 묻지 않기 위함. 다만 **기본값이 GROUP이면
  목록 입력창에 그룹명을 상시 표시**해서 모르고 공유하는 사고를 막는다

### 미디어 한도 조회 — `GET /diaries/media/quota` 응답

```json
{
  "tier": "premium",
  "monthly": {
    "usedBytes": 524288000,
    "limitBytes": 2147483648,
    "remainingBytes": 1623195648,
    "resetsAt": "2026-09-01T00:00:00+09:00"
  },
  "total": {
    "usedBytes": 3221225472,
    "limitBytes": 21474836480,
    "remainingBytes": 18253611008
  },
  "perFileLimitBytes": 209715200,
  "videoAllowed": true,
  "maxVideoDurationMs": 300000
}
```

> `usedBytes`에는 **유효한 `PENDING` 예약분도 포함**한다. 그래야 업로드 중인 파일이
> 게이지에 반영되어, 사용자가 연달아 올리다 마지막에만 거부당하는 일이 없다.

> ⚠️ **동시 업로드 경합**: `reserve` 여러 건이 동시에 도달하면 한도를 넘길 수 있다.
> 사용자별 Redis 락으로 직렬화한다. 백엔드에 이미 `redis` 모듈이 있으므로 재사용한다.

### 서버 측 2차 최적화는 하지 않는다
presigned 직접 업로드로 바뀌면서 서버는 바이트를 보지 못한다. 따라서 **압축은 전적으로
클라이언트 책임**이고, 서버는 검증(크기·타입·길이)만 한다. 이는 오히려 서버 CPU를
아끼는 방향이며, 사용자가 "원본 업로드"를 고른 경우 서버가 다시 압축하면 그 선택을
무시하는 셈이라 일관성 면에서도 맞다.
- 예외: **웹(kIsWeb)** 은 클라이언트 압축이 불가하다. 웹은 Phase 2 범위에서 제외하고,
  지원 시점에 별도 판단한다. (모바일 우선 기능)

## 4. 클라이언트 압축 전략 (Flutter)

기존 [editor_image_handler.dart](../../lib/shared/widgets/editor/mixins/editor_image_handler.dart)
의 `_compressImage`가 이미 `flutter_image_compress`를 쓰고 있으므로 **패턴을 재사용**하되,
다이어리용은 별도 유틸로 분리한다 (`lib/features/main/diary/data/utils/media_compressor.dart`).

### 이미지

| 모드 | 처리 |
|------|------|
| 압축 (기본) | 최대 변 1920px, quality 80, JPEG/WebP |
| 원본 | 변환 없이 그대로 (단, 파일 1개 최대치는 적용) |

- `kIsWeb`에서는 `flutter_image_compress`가 동작하지 않는다. presigned 방식에서는 서버가
  대신 압축해줄 수도 없으므로, **웹은 Phase 2 미디어 첨부 대상에서 제외**한다
  (텍스트 일기는 웹에서도 정상 동작). 모바일 우선 기능으로 명시한다.
- GIF/SVG는 압축하지 않는다 (애니메이션 손실).
- **압축 결과가 원본보다 크면 원본을 쓴다** (기존 코드와 동일한 방어).

### 영상
- `flutter_image_compress`는 영상을 다루지 못한다. **`video_compress` 패키지 추가 필요.**
- 압축 모드: 720p / 중간 비트레이트. 원본 모드: 그대로.
- 영상 압축은 수십 초가 걸릴 수 있으므로 **진행률 표시와 취소 버튼이 필수**다.
- 썸네일은 클라이언트에서 첫 프레임을 추출해 함께 올린다 (서버 ffmpeg 부담 감소).

### 업로드 전 사용자 안내 (핵심 UX)
파일을 고른 직후, 업로드하기 전에 **압축 여부를 선택하는 시트**를 띄운다.

```
┌─────────────────────────────────┐
│  사진 3장 추가                    │
│                                 │
│  ◉ 압축해서 올리기                │
│     24.3 MB → 3.1 MB (87% 절약)  │
│                                 │
│  ○ 원본 그대로 올리기              │
│     24.3 MB                     │
│                                 │
│  이번 달 남은 용량 1.5 GB          │
│  [ 취소 ]        [ 올리기 ]       │
└─────────────────────────────────┘
```

- 압축 후 예상 크기는 **실제로 압축해본 뒤** 보여준다 (추정치 금지 — 어긋나면 신뢰를 잃는다).
- 남은 용량을 넘기면 "올리기"를 비활성화하고 사유를 명시한다.

### 4-1. 본문(Delta)과 미디어의 경계 ★모호했던 부분

메모 기능은 이미지를 **Delta 안에 임베드**하면서 `MemoAttachment` 테이블도 함께 두고 있는데,
둘이 **서로 동기화되지 않는다**(본문에서 이미지를 지워도 attachment 레코드와 R2 파일은 남는다).
메모에서는 단순한 지저분함이지만, **다이어리에서는 그대로 한도 누수**가 된다.

**결정: 다이어리 본문 Delta에는 미디어를 임베드하지 않는다.**

| | 위치 | 관리 주체 |
|---|------|----------|
| 텍스트·서식·체크리스트 | `content` (Delta JSON) | Quill 에디터 |
| 사진·영상 | `DiaryMedia` 레코드 | **미디어 그리드 (본문과 분리)** |

- 에디터 툴바에서 **이미지 삽입 버튼을 제거**한다. 사진은 본문 아래 전용 그리드로만 추가한다.
- 이렇게 하면 "본문 Delta를 파싱해 어떤 이미지가 살아있는지 diff 비교" 하는 로직 자체가
  **필요 없어진다.** 미디어 추가/삭제가 곧 레코드 추가/삭제이므로 상태가 항상 일치한다.
- UX 손실도 크지 않다. 일기는 "글 중간중간 사진 배치"보다 **"그날의 사진 모음 + 글"** 이
  자연스러운 형태이고, 그리드 쪽이 썸네일 목록·전체화면 뷰어·순서 변경과도 잘 맞는다.
- 향후 본문 중간 배치가 꼭 필요해지면, Delta에 **`mediaId`만 참조하는 커스텀 임베드**를
  넣는 방식으로 확장한다 (URL 직접 임베드 금지 — 참조를 mediaId로 두면 그때도
  소유권이 `DiaryMedia`에 남아 누수가 생기지 않는다).

```
│ ┌─────────────────────────────┐ │
│ │ 8/31 일 · 🌧️  [👨‍👩‍👧 가족]     │ │  ← 사진 없으면 텍스트 카드
│ │ 비 와서 집에만 있었다…        │ │
│ └─────────────────────────────┘ │
├─────────────────────────────────┤
│ [📷] 오늘 어땠나요?        [↑]  │  ← ★ 빠른 기록 바 (하단 고정)
└─────────────────────────────────┘
```

#### 뷰 전환 — 3종
앱바 `⋮` 또는 상단 탭으로 전환한다. **기본은 타임라인.**

| 뷰 | 성격 | 언제 쓰나 |
|---|------|----------|
| **타임라인** (기본) | 흘려보기 | 그냥 들춰볼 때 — 월 구분선 있는 무한 스크롤 |
| **사진 그리드** | 사진으로 더듬기 | "그때 그 사진" 찾을 때 — 정사각 썸네일만 빽빽하게 |
| **캘린더** | 날짜로 찾기 | 특정 날짜를 알 때 — `table_calendar` |

> 캘린더를 기본에서 뺀 이유: 캘린더는 **날짜를 이미 알 때** 쓰는 뷰다.
> 대부분의 열람은 "그냥 보고 싶어서"이므로 타임라인이 기본이어야 한다.

#### 카드 — 사진 우선
- 사진이 있는 날: **사진이 카드의 주인공**, 날짜·기분·본문 일부를 아래 얹음
- 사진이 없는 날: 텍스트 카드로 축소 (높이를 낮춰 리듬을 만든다)
- 사람은 글보다 사진으로 기억을 더듬는다. 기존 "썸네일 붙은 텍스트 카드"를 뒤집은 것

#### 공개 범위 시각 구분
필터를 "전체"로 둔 상태에서도 내 일기와 그룹 공유 일기가 한눈에 구분되어야 한다.
그룹 일기가 섞여 있는 줄 모르고 쓰면 사생활 사고가 난다.
- 카드: 그룹 일기에만 **그룹명 칩 + 작성자 아바타** 표시 (내 비공개 일기엔 없음)
  → 뱃지를 "비공개"에 다는 게 아니라 **"공유됨"에 다는 것**이 맞다. 기본이 비공개이므로
    예외인 쪽을 표시해야 눈에 걸린다.
- 캘린더 뷰: 날짜 셀 우상단에 작은 그룹 색상 점 (`personalColor` 활용)
- 같은 날 내 일기와 그룹원 일기가 함께 있으면 캘린더 셀에 **개수 뱃지**.
  하루 1편은 **사용자별** 제약이므로 그룹 뷰에서는 한 날짜에 여러 사람 일기가 존재한다
- 상단 `GroupFilterBar` (기존 공용 위젯)

#### 기타
- 검색 (제목·본문 평문)
- 앱바 `⋮`: 뷰 전환 / 저장공간 관리 / 온보딩 다시 보기
- 상태 3종: 로딩(`shimmer`) / 에러(`AppErrorState`) / 빈 상태(`AppEmptyState`)
  - **빈 상태에서도 빠른 기록 바는 살아있어야 한다.** "첫 기록을 남겨보세요" 정도만 띄우고
    입력창으로 시선을 유도한다 (빈 화면 + 안내문만 있으면 이탈한다)

### 5-1-A. 빠른 기록 바 (`quick_capture_bar`) ★ 핵심

하단 고정. 이 기능의 성패가 여기 달려 있다. **탭 수를 최소로 유지하는 것이 전부**다.

```
접힘:  [📷]  오늘 어땠나요?              [↑]
펼침:  [📷]  점심에 본 고양이|            [↑]
       ┌──────────────────────────┐
       │ [사진1] [사진2] [+]       │  ← 첨부 대기 썸네일
       └──────────────────────────┘
```

**동작 원칙**
- 텍스트 입력 후 `↑` → **즉시 append, 화면 전환 없음.** 입력창이 비고 타임라인 최상단
  카드가 갱신된다 (낙관적 갱신 — 서버 응답을 기다리지 않는다)
- `📷` → 갤러리/카메라 → 압축 선택 시트 → 업로드 → append.
  **텍스트 없이 사진만 던지는 것도 허용**한다 (오히려 이쪽이 더 잦다)
- 전송 실패 시 입력 내용을 **복원**하고 재시도 버튼을 띄운다. 조용히 날리지 않는다
- 키보드가 올라오면 바가 키보드 위로 따라 올라간다 (`viewInsets.bottom`)
- **오늘 일기가 이미 있으면** 입력창 placeholder가 "이어서 기록하기"로 바뀐다
  → 덮어쓰는 게 아니라 이어붙는다는 걸 문구로 알린다

**하지 말 것**
- 기분·날씨·공개범위를 여기서 묻지 않는다. 물어보는 순간 빠른 기록이 아니다
- 저장 완료 스낵바를 띄우지 않는다. 카드가 갱신되는 것 자체가 피드백이다
- 글자수 제한을 두지 않는다 (길게 쓰면 그대로 append)

**"오늘 정리하기" 진입**
- 오늘 카드를 탭하면 상세, 상세에서 "다듬기" → `diary_form_screen`
- 조각이 2개 이상 쌓인 날의 카드에는 **"정리하기" 힌트**를 작게 노출

### 5-1-B. 회고 — "n개월 전 오늘" (`flashback_card`) ★

타임라인 최상단에 카드로 노출. **찾으러 가지 않아도 올라오는** 유일한 뷰다.

- 대상: **1개월 / 3개월 / 6개월 / 1년 / n년** 전 오늘
  → 1년만 두면 초기 사용자에게 아무것도 안 보인다. **1개월부터 시작**해야 첫 달부터 작동
- 여러 개가 걸리면 **가장 오래된 것 하나**만 (오래될수록 반가움이 크다)
- 사진이 있는 회고를 우선 노출
- 없으면 카드 자체를 렌더링하지 않는다 (빈 카드로 자리 차지 금지)
- 탭하면 그날 상세로 이동
- **알림은 Phase 3에서 별도 판단.** 매일 푸시는 피로도가 크다.
  넣더라도 "사진이 있는 회고가 있을 때만" 정도로 제한한다

### 5-2. 다듬기 화면 (`diary_form_screen`)

> **위상 변화** — 빠른 기록이 생기면서 이 화면은 "쓰는 곳"이 아니라 **"다듬는 곳"** 이 된다.
> 진입하면 그날 던진 조각이 이미 본문에 시각 마커와 함께 들어 있고, 사용자는 거기서부터
> 정리한다. **백지에서 시작하지 않는다는 것이 이 화면의 존재 이유**다.
> (조각이 없는 날에 직접 진입하면 종전처럼 빈 에디터로 시작한다)

- 상단: 날짜 선택 (기본 오늘, 과거 날짜 선택 가능 / **미래 날짜 금지**)
- **시각 마커 일괄 제거 버튼** — 조각들을 하나의 글로 합치고 싶은 사용자를 막지 않는다
- 기분 선택 (이모지 칩) · 날씨 (weather 기능에서 자동 채움, 수정 가능)
- 제목 (선택)
- 본문: 기존 공용 `RichTextEditor` (flutter_quill, Delta 저장) 재사용
- 미디어 첨부 영역: 그리드 + `+` 버튼 → 갤러리/카메라 선택 → 압축 선택 시트
  - 첨부 항목은 드래그로 순서 변경, 길게 눌러 삭제
  - 상단에 **한도 게이지 바** 상시 표시
- 공개 범위: PRIVATE / GROUP 선택 (GROUP이면 그룹 선택 필수)
- 하단: `FormBottomBar` 고정 저장 버튼 (프로젝트 컨벤션)
- **자동 임시저장** — 미디어를 올려놓고 앱이 죽으면 고아 파일이 생기므로,
  미디어 첨부 시점에 로컬 draft를 남겨 복구할 수 있게 한다

#### 키보드·스크롤 간섭 대응 ★
날짜·기분·날씨·제목·본문·미디어 그리드·한도 게이지·공개범위까지 한 화면 요소가 많다.
모바일에서 키보드가 올라오면 본문 영역이 좁아져 답답해지므로:

- **메타 영역 접기** — 날짜/기분/날씨/공개범위를 상단 **접이식 헤더** 한 줄로 요약하고
  (`2026-09-01 · 😊 · ☀️ · 비공개`), 탭하면 펼쳐 수정한다. 기본은 접힘.
  → 작성 화면 진입 직후 사용자가 실제로 원하는 건 "쓰기"다. 설정은 부차적이다.
- **본문 포커스 시** 메타 헤더와 미디어 그리드를 자동으로 접어 본문에 세로 공간을 몰아준다.
- **에디터 툴바는 키보드 바로 위에 고정** (`MediaQuery.viewInsets.bottom` 반영).
  `FormBottomBar` 저장 버튼은 키보드가 올라오면 숨기고, 툴바에 자리를 내준다
  (둘이 겹치면 Android에서 저장 버튼이 툴바 뒤로 들어간다 — `vibe-verify` 점검 항목).
- 한도 게이지는 미디어 그리드를 펼쳤을 때만 보인다 (상시 노출은 압박감만 준다).
- `ScrollableFormBody`(기존 공용 위젯) 사용 + 포커스 시 해당 필드로 자동 스크롤.

### 5-3. 상세 화면 (`diary_detail_screen`)
- 헤더: 날짜(크게) + 기분 + 날씨 + 작성자(그룹 공개일 때)
- 미디어 갤러리: 그리드 → 탭하면 전체화면 뷰어 (스와이프, 핀치 줌, 영상 재생)
- 본문: 기존 `RichTextViewer` 재사용
- 앱바 액션: 수정 / 삭제 / 공유 — **전경색 명시 필수** (DESIGN.md 1-3)

### 5-4. 저장공간 관리 (`diary_storage_screen`) ★ 차별점
한도제에서 사용자가 가장 답답해하는 건 "뭐가 용량을 잡아먹는지 모르는 것"이다.
- 월간/누적 한도 게이지 (남은 용량, 리셋일)
- **용량 큰 미디어 Top N 목록** — 썸네일·크기·소속 일기, 개별 삭제
- 원본으로 올린 파일 필터 → "압축본으로 교체" 제안
- 프리미엄이 아니면 하단에 업그레이드 CTA (기존 구독 화면으로 연결)

## 6. 구독 연동

### 6-1. 프리미엄 상품 활성화
[docs/features/subscription.md](subscription.md)의 "나중에 할 작업 1번"이 정확히 이 작업이다.
`iap_product_ids.dart` 주석에도 이 기능이 전제로 적혀 있다.

- `IapProductIds.all`에 `premiumMonthly` 추가
- **애플: 기존 구독 그룹 안에** 상품 등록 (그룹을 나누면 이중 결제가 가능해진다)
- 구글: 상품 + 기본 요금제 **둘 다 수동 활성화**
- 플랜 비교 카드가 2열 → **3열이 되므로 세로 스택으로 레이아웃 재작업 필요**

### 6-2. 업그레이드 유도 지점 (과하지 않게)
- 한도 초과로 업로드 실패했을 때 → 다이얼로그에서 "한도 늘리기"
- 저장공간 관리 화면 하단 CTA
- 잔여 용량 10% 미만일 때 게이지 색상 변경 + 안내 (배너 도배 금지)

> ⚠️ 무료 사용자가 **일기 작성 자체를 못 하게 막지 않는다.** 텍스트 일기는 전면 무료이고,
> 제한되는 것은 미디어 용량뿐이다. 핵심 기능을 인질로 잡으면 스토어 심사와 평점 양쪽에서
> 문제가 된다.

### 6-3. 문구 포지셔닝 — "제한"이 아니라 "제공"
같은 사실도 어떻게 쓰느냐에 따라 결제 압박으로 읽힌다. 심사자와 사용자 모두에게
**기본 제공량이 있다**는 인상을 먼저 준다.

| ❌ 피할 문구 | ✅ 권장 문구 |
|------------|------------|
| "무료 플랜은 100MB로 제한됩니다" | "매월 100MB를 무료로 제공합니다" |
| "용량이 부족합니다. 결제하세요" | "이번 달 무료 용량을 모두 사용했어요. 다음 달 1일에 초기화됩니다" |
| "프리미엄 전용 기능" | "프리미엄에서는 더 넉넉하게 쓸 수 있어요" |

- 한도 초과 안내에는 **결제 외 대안을 반드시 함께** 제시한다 —
  ① 다음 달 리셋 안내 ② 저장공간 관리로 정리하기 ③ 압축해서 다시 시도.
  결제 버튼만 있는 막다른 다이얼로그는 심사에서 지적받기 쉽고 평점도 깎인다.
- 게이지에는 **남은 양**을 강조한다("1.5GB 남음"), 쓴 양이 아니라.

## 7. 다국어 (l10n)

- prefix: `diary_`
- **4개 파일 모두 필수**: `app_ko.arb`, `app_en.arb`, `app_ja.arb`, `app_zh.arb`
- 용량 표기는 로케일마다 단위 표기가 다르므로 포맷 헬퍼를 하나 두고 통일한다
- 주요 키: `diary_title`, `diary_empty`, `diary_quota_monthly`,
  `diary_quota_exceeded`, `diary_compress_option`, `diary_keep_original`,
  `diary_storage_manage`, `diary_streak_days` 등
- 빠른 기록·회고 관련: `diary_capture_hint`("오늘 어땠나요?"),
  `diary_capture_hint_continue`("이어서 기록하기"), `diary_capture_failed`,
  `diary_polish`("정리하기"), `diary_flashback_months`, `diary_flashback_years`
- ⚠️ **회고 문구는 복수형 처리 필요** — "3개월 전"은 한국어에선 문제없지만
  영어는 `1 month ago` / `3 months ago`로 갈린다. ARB **plural 문법**을 쓴다
- ⚠️ 빠른 기록 placeholder는 **직역하면 어색해진다.** 각 언어에서 자연스러운
  구어체로 (일본어 `今日はどうでしたか`, 중국어 `今天过得怎么样` 등)

## 8. 구현 순서 (권장)

### Phase 1 — 텍스트 일기 + 빠른 기록 (미디어 없이)
1. 백엔드: Prisma 모델 + 마이그레이션 + `/diaries` CRUD
   + **`/diaries/append`(upsert)** + `diaryDateInKst()` (새벽 4시 경계)
2. 프론트: 모델/레포/프로바이더
3. **타임라인 화면 + 빠른 기록 바** (텍스트만) — 이 기능의 심장
4. 상세 / 다듬기 화면 (시각 마커 렌더링·제거)
5. 라우트 등록 (`app_routes.dart`, `main_routes.dart`) + 더보기 탭 연결
6. l10n 4개 언어

> 여기까지만으로도 **독립적으로 출시 가능한 기능**이 된다.
> 빠른 기록을 Phase 2로 미루지 않는 이유: 이게 없으면 그냥 흔한 일기 앱이고,
> **사용 습관은 초기에 붙는다.** 나중에 넣으면 이미 떠난 뒤다.

### Phase 2 — 이미지 첨부 + 한도 (모바일 전용)
7. 백엔드: `DiaryMedia` + 한도 집계 서비스 + `/media/quota`·`/reserve`·`/confirm`
   + Redis 락 + **정리 스케줄러 2종**(PENDING 15분 / 고아 24시간)
8. 프론트: 압축 유틸(이미지) + 압축 선택 시트 + 미디어 그리드 + 한도 게이지
   + presigned PUT 업로드(진행률·재시도)
9. **빠른 기록 바에 사진 첨부 연결** + EXIF 날짜 확인 (0-4)
10. **사진 그리드 뷰** + 카드 사진 우선 레이아웃
11. 저장공간 관리 화면
12. **회고("n개월 전 오늘") 카드** — 사진이 있어야 위력이 나오므로 여기서 붙인다

### Phase 3 — 영상 + 프리미엄 판매
13. `video_compress` 도입, 영상 업로드/재생/썸네일
14. 프리미엄 상품 스토어 등록 + `IapProductIds.all` 추가 + 플랜 비교 3열 재작업
15. 캘린더 뷰, 연속 작성(스트릭), 대시보드 위젯
16. 회고 알림(선택 — 피로도 검토 후), 일기+미디어 **내보내기(ZIP)**

> **내보내기를 넣는 이유**: 미디어를 쌓게 하는 기능은 필연적으로
> "내 추억을 인질로 잡힌 것 아닌가"라는 불안을 만든다. 계정 삭제·구독 해지 시점에
> 일괄 내보내기가 있으면 그 불안이 줄고, 오히려 구독 유지에 도움이 된다.

## 9. 미리 짚어둘 위험 요소

| 위험 | 대응 |
|------|------|
| **빠른 기록 연타 시 unique 충돌** — 같은 날짜 동시 upsert | 트랜잭션 + P2002 1회 재시도 (append 스펙) |
| **자정~새벽 기록이 다음날로 감** | 하루 경계 04:00 KST (`diaryDateInKst()`) — **모든 뷰가 동일 기준** (0-2) |
| **빠른 기록이 모르고 그룹에 공유됨** | 새 일기일 때만 기본값 적용 + 입력창에 그룹명 상시 표시 |
| **append 실패로 입력 유실** | 낙관적 갱신 + 실패 시 입력 복원·재시도 (조용히 날리지 않음) |
| **날짜 타임존 어긋남** — unique 충돌·조회 밀림 | `'YYYY-MM-DD'` 문자열 규약 + `date-kst.util.ts` 재사용 (3-1) |
| **presigned 크기 위조** — 1KB 예약 후 200MB 업로드 | `confirm`에서 `HeadObject` 실측 후 초과분 삭제·402 (3-2) |
| **PENDING 예약 누수** — URL만 받고 안 올림 | 15분 경과 `PENDING` 정리 스케줄러 |
| **고아 미디어 누수** — 저장 안 하고 나간 첨부 | 24h 스케줄러 정리 + 로컬 draft 복구 |
| **삭제 후 재업로드 반복으로 실질 무한 용량** | 미디어는 즉시·영구 삭제 + 월간 한도는 회복 안 함 (1장) |
| **동시 업로드로 한도 초과** | Redis 사용자 락 + `confirm` 트랜잭션 내 재집계 |
| **본문 Delta와 미디어 불일치** | Delta에 미디어를 임베드하지 않음 — 구조적으로 제거 (4-1) |
| **확장자·MIME 위조 업로드** | `reserve`에서 화이트리스트, `confirm`에서 Content-Type 재확인 |
| **영상 압축 중 앱 종료** | 진행률 + 취소 버튼, 임시파일 정리 |
| **다운그레이드 시 초과 상태** | 신규 업로드만 차단, 기존 데이터 유지 |
| **R2 비용 폭증** | 출시 초기 한도를 보수적으로 잡고, 통계 보고 상향 |
| **웹에서 압축 불가** | 웹은 Phase 2 미디어 대상에서 제외 (텍스트는 정상 동작) |
| **웹 presigned CORS 미설정** | 웹 지원 시 R2 버킷 CORS(PUT + 오리진) 설정 |
| **그룹 일기를 비공개로 착각** | 목록·캘린더에 공유 뱃지 노출 (5-1) |
| **그룹 삭제 시 GROUP 일기** | 그룹 삭제 영향도 — `vibe-verify` 체크리스트 항목 |

## 10. 필요한 신규 의존성

| 패키지 | 용도 | Phase |
|--------|------|-------|
| `video_compress` | 영상 압축·썸네일 추출 | 3 |
| `video_player` | 영상 재생 | 3 |
| `photo_view` | 이미지 핀치 줌 뷰어 | 2 |

> `image_picker`, `flutter_image_compress`, `cached_network_image`,
> `flutter_quill`, `table_calendar`, `dio`(presigned PUT + 진행률)는 **이미 설치되어 있다.**
>
> **백엔드 신규 의존성 없음** — presigned 직접 업로드로 바꾸면서 서버가 바이트를 다루지
> 않으므로 `sharp` 확장이나 `ffmpeg`가 필요 없다. `@aws-sdk/s3-request-presigner`,
> `redis`, `dayjs`, `date-kst.util.ts` 모두 이미 있다.
