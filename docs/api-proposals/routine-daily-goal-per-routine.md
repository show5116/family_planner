# 일일 목표 — 습관별 포함/제외 설정 (2차)

> **상태**: ✅ 구현 완료 (백엔드·프론트 2026-08-21)
> **작성일**: 2026-08-21
> **선행 문서**: [routine-daily-goal.md](routine-daily-goal.md) (1차, 구현 완료)

---

## 배경 — 1차 구현에서 드러난 문제

1차로 도입한 일일 목표는 "그날 대상 습관 중 N개를 채우면 달성"입니다. 그런데 서버가 쓰는 **"그날 대상 습관 수"(`totalCount`)의 정의가 "해당 날짜에 활성 상태였던(일시정지 제외) 루틴 수"** 라서, 반복주기가 전혀 반영되지 않습니다.

그 결과:

| 습관 | 실제 수행 주기 | 현재 일일 목표 분모 |
|---|---|---|
| 아침 스트레칭 (DAILY) | 매일 | 매일 포함 ✅ 타당 |
| 운동 (WEEKLY, 주 3회) | 주 3일 | **매일 포함** ⚠️ |
| 대청소 (MONTHLY, 월 2회) | 월 2일 | **매일 포함** ⚠️ |
| 영어공부 (WEEKLY FIXED_DAYS, 월·수·금) | 주 3일 | **매일 포함** ⚠️ |

습관 15개 중 주/월간 습관이 5개면, 그 5개는 대부분의 날에 구조적으로 체크될 수 없는데도 분모에 남습니다. 목표를 10개로 잡아도 달성이 불가능한 날이 생겨, **"포기하지 않게 만든다"는 이 기능의 목적 자체가 훼손**됩니다.

## 검토 과정과 결정

서버가 "주 3회를 이번 주에 다 채웠는지"를 날마다 판정해 분모에서 자동으로 빼는 방식(동적 제외)도 검토했습니다. 하지만 **사용자가 습관별로 포함/제외를 직접 정하는 방식**으로 결정했습니다.

이유:
- 개별 설정이 있으면 동적 판정이 불필요합니다. 부담스러운 항목은 사용자가 직접 빼면 됩니다.
- 동적 제외는 "주 3회를 다 채우면 그날 목록에서 습관이 사라지는" 부작용이 있어, 사용자가 "내 습관이 어디 갔지?"라고 당황할 수 있습니다.
- 계산이 단순해집니다: **"포함으로 지정된 습관 중 오늘 체크한 수"**. 주기 판정 로직이 서버에 들어가지 않습니다.

### ⚠️ 이 결정의 트레이드오프 (프론트에서 UI 문구로 처리)

주 3회 습관을 **포함**시키면, 그 주에 3회를 다 채운 뒤에도 남은 4일 동안 계속 미체크 상태로 분모에 남습니다. 즉 **"포함 = 사실상 매일 하는 습관으로 취급"** 입니다. 이 의미를 설정 화면에서 분명히 전달해, 사용자가 알고 선택하도록 만들 예정입니다.

## 요청 사항

### 1. `Routine`에 `includeInDailyGoal` 필드 추가

```prisma
model Routine {
  // ... 기존 필드

  /// 일일 목표 집계에 포함할지 여부.
  /// 기본값은 frequencyType에 따라 결정한다(아래 마이그레이션 항목 참고).
  includeInDailyGoal Boolean @default(true)
}
```

**응답에 포함이 필요한 엔드포인트**: `Routine` DTO를 반환하는 모든 곳(`GET /routines`, `GET /routines/:id`, `POST /routines`, `PATCH /routines/:id` 등). 프론트는 목록 화면에서 이 값을 읽어 설정 화면을 구성합니다.

```json
{
  "id": "uuid",
  "title": "운동",
  "frequencyType": "WEEKLY",
  "weeklyMode": "COUNT_ONLY",
  "targetCount": 3,
  "includeInDailyGoal": false   // ▼ 신규
}
```

### 2. `POST /routines` / `PATCH /routines/:id`에서 수정 가능하도록

```json
{ "includeInDailyGoal": false }   // 옵션. 생략 시 생성은 기본값 적용, 수정은 미변경
```

### 3. 기존 데이터 마이그레이션 기본값

이 필드가 없던 기존 습관들의 초기값을 **주기에 따라 다르게** 설정해 주세요. 전부 `true`로 넣으면 지금의 문제가 그대로 남고, 전부 `false`로 넣으면 일일 목표가 빈 껍데기가 됩니다.

| frequencyType | 초기값 | 근거 |
|---|---|---|
| `DAILY` | `true` | 매일 하는 습관이므로 당연히 포함 |
| `WEEKLY` (COUNT_ONLY, FIXED_DAYS 모두) | `false` | 매일 대상이 아니므로 기본 제외 |
| `MONTHLY` | `false` | 매일 대상이 아니므로 기본 제외 |

> 신규 생성 시 기본값도 동일한 규칙을 적용해 주시면 좋겠습니다. 즉 `POST /routines`에서 `includeInDailyGoal`을 생략하면 `frequencyType`이 `DAILY`일 때만 `true`.

### 4. 일일 목표 관련 계산에 이 필드 반영

1차로 구현된 아래 값들의 계산에서, **`includeInDailyGoal = false`인 습관은 전부 제외**해 주세요.

| 엔드포인트 | 영향받는 필드 |
|---|---|
| `GET routines/stats/overview` | `heatmap[].totalCount`, `heatmap[].goalAchieved`, `goalAchievedDays`, `goalTotalDays`, `goalAchievementRate` |
| `GET routines/stats/daily-streak` | `todayCheckedCount`, `todayTargetCount`, `todayAchieved`, `currentStreakDays`, `longestStreakDays`, `recent14Days.*` |

- `dailyGoalMode=ALL`일 때의 "그날 대상 습관 전부"도 **포함으로 지정된 습관 전부**로 해석해 주세요.
- 포함으로 지정된 습관이 0개인 날은 기존 규칙대로 집계 대상에서 제외(`goalAchieved: null`, `goalTotalDays`에서 제외)해 주세요.

> ⚠️ `totalChecked` / `totalExpected` / `achievementRate`(1차 이전부터 있던 전체 달성률)는 **기존 정의 그대로 두고 이 필드의 영향을 받지 않게** 해주세요. 전체 통계와 일일 목표 통계는 서로 다른 축의 지표입니다.

## 열린 질문에 대한 결정

1. **벌크 엔드포인트는 구현됨** — `PATCH routines/daily-goal-inclusions`. 설정 화면에서 변경된 항목만 모아 한 번에 전송한다.
2. 목표 개수가 포함 습관 수를 넘는 경우는 **프론트에서 차단**하는 방식으로 정리했다. 슬라이더 상한이 포함 습관 수이고, 스위치를 꺼서 포함 수가 줄면 목표도 자동으로 함께 낮아진다. 서버 보정은 필요 없다.

## 열린 질문

1. **`includeInDailyGoal`을 `PATCH /routines/:id`로 하나씩 바꾸는 것 외에, 일괄 변경 엔드포인트가 필요할까요?** 프론트 설정 화면에서 여러 습관을 한 번에 토글한 뒤 저장하는 UX를 고려 중입니다. 습관이 20~30개면 PATCH를 그만큼 연속 호출하게 되는데, 다음 형태의 벌크 엔드포인트가 있으면 깔끔합니다. 백엔드 부담이 크지 않다면 요청드립니다.

   ```
   PATCH /routines/daily-goal-inclusions
   { "items": [ { "id": "uuid", "includeInDailyGoal": true }, ... ] }
   ```

   없다면 프론트에서 변경된 항목만 골라 개별 PATCH를 병렬 호출하는 방식으로 처리하겠습니다.

2. **목표 개수(`dailyGoalCount`)가 포함 습관 수보다 커지는 경우**의 처리입니다. 예: 포함 습관이 8개인데 목표가 10개. 1차 문서에서 "습관 총 개수보다 큰 값도 허용"으로 합의했으니 그대로 두면 될 것 같은데, 이제는 **달성이 영구히 불가능**해지는 상황이라 좀 더 적극적인 처리가 필요할 수 있습니다.
   - **프론트 계획**: 설정 화면에서 포함 습관 수를 실시간으로 보여주고, 목표가 그보다 크면 경고 문구를 띄웁니다. 슬라이더 상한도 포함 습관 수로 제한합니다.
   - **백엔드 확인 요청**: 이 경우 서버에서 별도 보정 없이 그대로 두면 되는지, 아니면 `todayTargetCount`를 포함 습관 수로 클램프하는 게 나을지 의견 부탁드립니다. 프론트 선호는 **보정 없이 그대로**(설정값을 서버가 임의로 바꾸면 사용자가 혼란스러움)입니다.

## 프론트 구현 계획

**설정 화면 개편** (`routine_daily_goal_screen.dart`)

기존 "모드 선택 + 개수 슬라이더" 아래에 **집계 대상 습관 목록** 섹션을 추가합니다.

- 습관마다 스위치(포함/제외) + 주기 배지를 표시: `매일`, `주 3회`, `월·수·금`, `월 2회`
- **주기별로 그룹핑**해서 보여줍니다. "매일" 그룹은 대부분 켜져 있을 테니 접어두고, **주간/월간 그룹을 펼쳐서** 사용자가 판단해야 할 항목이 먼저 눈에 들어오게 합니다.
- 주간/월간 습관의 스위치 아래에는 트레이드오프를 명시: *"켜면 이 습관을 매일 해야 하는 것으로 계산해요"*
- 상단에 실시간 요약: *"매일 8개 중 6개가 목표"* — 포함 습관 수가 바뀌면 즉시 갱신
- 목표 개수 슬라이더의 상한을 **포함 습관 수**로 제한하고, 포함 수가 줄어 목표를 넘기면 자동으로 낮춰 경고 표시

이렇게 하면 사용자가 "어떤 습관이 왜 목표 달성을 어렵게 만드는지"를 한 화면에서 파악하고 바로 조정할 수 있습니다.
