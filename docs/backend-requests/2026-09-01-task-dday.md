# 백엔드 요청 — 할일 D-Day(`daysUntilDue`) 계산 수정

- **작성일**: 2026-09-01
- **대상**: `GET /tasks`, `GET /tasks/:id` 및 Task를 반환하는 모든 엔드포인트
- **관련 파일**: `src/task/task.service.ts` (`calculateDaysUntilDue`), `src/task/dto/task-response.dto.ts`
- **우선순위**: 중 (오표기이지만 데이터 손상은 없음)

---

## 현상

할일 목록에서 **오늘 마감인 항목이 `D-1`로 표시**되고, **마감이 지난 항목도 `D-Day`로 표시**됩니다.

앱은 서버가 주는 `daysUntilDue`를 그대로 `D-{n}`으로 그립니다. 값 자체가 어긋나 있습니다.

## 원인

```ts
// src/task/task.service.ts:817
private calculateDaysUntilDue(dueAt: Date | null, now?: Date): number | null {
  if (!dueAt) return null;
  const currentTime = now || new Date();
  const due = new Date(dueAt);
  const diffTime = due.getTime() - currentTime.getTime();
  return Math.ceil(diffTime / (1000 * 60 * 60 * 24));   // ← 시각 차이를 올림
}
```

**날짜(달력상 며칠 남았는지)가 아니라 시각 차이를 올림 처리**하고 있어 두 가지 문제가 생깁니다.

### 문제 1 — 같은 날 마감인데 시각에 따라 값이 갈립니다

현재 시각이 `2026-09-01 09:14 KST` 일 때:

| 마감 | 기대값 | 실제값 |
|---|---|---|
| 오늘 20:00 | `0` (D-Day) | **`1`** |
| 오늘 22:00 | `0` (D-Day) | **`1`** |
| 오늘 09:00 (이미 지남) | `0` (D-Day) | `0` |
| 3일 뒤 15:00 | `3` | **`4`** |

아직 남은 시간이 있으면 올림되어 하루가 더 붙습니다.

### 문제 2 — 지난 할일이 음수로 내려가지 않습니다

| 마감 | 기대값 | 실제값 |
|---|---|---|
| 어제 20:00 | `-1` (하루 지남) | **`0`** |

`Math.ceil`은 `-0.6` 을 `-0` 으로 올리므로, **하루 이내로 지난 할일이 전부 `0`** 이 됩니다.
결과적으로 앱에서 "오늘 마감"과 "어제 지난 할일"을 `daysUntilDue`만으로 구분할 수 없습니다.

### 문제 3 — 시간대

`new Date()` 는 서버 기준(UTC)입니다. 사용자는 KST 기준으로 날짜를 인식하므로
UTC 자정을 넘는 구간에서 하루가 어긋납니다.

---

## 요청

`daysUntilDue` 를 **KST 달력 날짜 기준 차이**로 계산해 주세요.

- 오늘 마감 → `0`
- 내일 마감 → `1`
- 어제 마감 → `-1`

```ts
private calculateDaysUntilDue(dueAt: Date | null, now?: Date): number | null {
  if (!dueAt) return null;

  // KST 기준 '날짜'만 뽑아 비교합니다. 시·분은 무시합니다.
  const KST_OFFSET_MS = 9 * 60 * 60 * 1000;
  const toKstDateOnly = (d: Date) => {
    const kst = new Date(d.getTime() + KST_OFFSET_MS);
    return Date.UTC(kst.getUTCFullYear(), kst.getUTCMonth(), kst.getUTCDate());
  };

  const dueDay = toKstDateOnly(new Date(dueAt));
  const today = toKstDateOnly(now ?? new Date());

  return Math.round((dueDay - today) / (1000 * 60 * 60 * 24));
}
```

### 검증 케이스

`now = 2026-09-01T00:14:00Z` (KST 09:14, 9월 1일) 기준

| dueAt | 기대 `daysUntilDue` |
|---|---|
| `2026-09-01T11:00:00Z` (오늘 20:00 KST) | `0` |
| `2026-09-01T00:00:00Z` (오늘 09:00 KST) | `0` |
| `2026-09-04T06:00:00Z` (9/4 15:00 KST) | `3` |
| `2026-08-31T11:00:00Z` (어제 20:00 KST) | `-1` |
| `2026-08-29T11:00:00Z` (사흘 전) | `-3` |
| `dueAt = null` | `null` |

## 앱 쪽 대응

서버 수정이 반영되면 앱은 값을 그대로 쓰면 됩니다. 표기는 이렇게 됩니다.

| `daysUntilDue` | 표시 |
|---|---|
| `0` | `D-Day` |
| `3` | `D-3` |
| `-2` | `D+2` (2일 지남) |

**서버 수정 전까지 앱에서 보정하지 않겠습니다.** 양쪽에서 각각 조정하면
서버가 고쳐진 뒤 다시 어긋나기 때문입니다. 배포 순서만 알려주시면 맞추겠습니다.

## 참고 — 기념일은 별도 필드입니다

기념일(`GET /tasks/anniversaries`)은 `daysSince`(당일 0)와 `dayCount`(당일 1일째, 한국식)를
따로 내려주고 있어 이번 건과 무관합니다. 할일도 같은 방식으로 두 값을 주는 방안이 있다면
그쪽도 괜찮습니다. 다만 **하나만 준다면 당일 0 기준**이 앱 표기와 맞습니다.
